Vidnux

0.1.0

A queue-based video converter for Linux that hands your footage to an editor without touching a single pixel it did not have to.

Created by dewakuneiei · MIT licensed · powered by ffmpeg

01What it is for

The short version, and the reason it exists.

The free build of DaVinci Resolve on Linux ships without an H.264/H.265 decoder and without an AAC decoder. That is a licensing gap, not a bug — but the result is that most phone and camera files import as offline, silent, or refuse to import at all.

Vidnux converts them to a format Resolve always accepts — DNxHR in a MOV with PCM audio — and does it for a whole folder at a time. Unlike the older DNxHD, DNxHR has no fixed table of permitted resolutions and frame rates, so 48 fps, 60 fps and 23.976 fps footage all pass through untouched at whatever size they already are.

It converts to seven other formats too, but that is the case it was built for.

02What it will never do to your footage

Every preset in Vidnux is built around one rule: never resample, never resize, never re-time. These are not settings you have to find — they are how the ffmpeg arguments are assembled, and several of them are enforced by tests in the repository.

  • Resolution is never changed.

    No scaling filter is ever added to the command. If a source has odd dimensions that a codec cannot accept, it is padded by a single pixel rather than resampled — so no existing pixel is ever recomputed. A test in preset.rs fails the build if a scale filter ever appears.

  • Frame rate is never changed.

    60, 50, 48, 30, 25, 24 and 23.976 fps all come out exactly as they went in. There is no -r and no fps filter anywhere. Editing formats are written as constant frame rate so a timeline stays in sync with variable-frame-rate phone recordings, but the rate itself is the source's own.

  • Colour is carried over, not guessed.

    Primaries, transfer characteristics, matrix and range are read off the source with ffprobe and written explicitly onto the output. This is what stops the washed-out or over-saturated result you get when a converter drops the tags and the player falls back to a guess.

  • Bit depth is kept.

    A 10-bit source stays 10-bit. Where a codec genuinely cannot carry it, Vidnux picks the closest pixel format that codec supports rather than silently dropping to 8-bit.

  • Audio is copied, not re-encoded.

    Whenever the target container can carry the source's audio stream as-is, it is copied byte for byte. When it cannot, it goes to PCM or FLAC — both lossless — never down to a lossy bitrate.

  • Every track survives.

    All audio tracks, subtitles in MKV, and file metadata are carried across when you leave Keep every audio / subtitle track ticked.

  • The source file is never modified.

    Vidnux only ever writes new files. If an output name is already taken it becomes name(1).mov, name(2).mov and so on — nothing is overwritten unless you explicitly ask for it.

  • The honest caveat.

    DNxHR, ProRes, AV1, H.264 and H.265 are compressed formats. At the default Visually lossless setting the result is not bit-identical to the source — it is indistinguishable by eye and safe to grade and re-render from. If you need mathematically identical output, use FFV1 / MKV or Ut Video / AVI, or the Lossless quality tier for H.264 / H.265 / AV1. Those are the only settings that are pixel-for-pixel identical, and they are much larger files.

03How a conversion actually runs

Nothing is hidden — you can read the exact command for any file before you start.

1
Inspect

ffprobe reads the real resolution, frame rate, codec, pixel format, audio codec and every colour tag from the source.

2
Assemble

The chosen target turns that into an argument list. Geometry and timing arguments are simply never emitted; colour and bit-depth arguments are copied from what step 1 found.

3
Claim a name

The output path is checked against the source, against every other job in the run, and against what is already on disk, before a single byte is written.

4
Encode

One ffmpeg process per job. Its progress output is parsed live into the percentage and the realtime multiplier you see on the row. Two to eight jobs run at once, as you choose.

See it for yourself

In the app: left panel → Advanced → Show the ffmpeg command per file. A DNxHR job looks roughly like this:

# no -s, no -vf scale, no -r, no fps filter — by construction
ffmpeg -i input.mkv \
  -c:v dnxhd -profile:v dnxhr_hq -pix_fmt yuv422p \
  -color_primaries bt709 -color_trc bt709 -colorspace bt709 \
  -c:a pcm_s16le \
  -map 0 -movflags +write_colr \
  output.mov

Vidnux checks which of these your ffmpeg was actually built with while the start-up banner is on screen, and greys out the ones it cannot produce. Plain Fedora's ffmpeg-free, for example, has no x264 or x265 — so those two are unavailable until you swap in the full RPM Fusion build.

Inputs: anything ffmpeg can read — mp4, mov, mkv, avi, wmv, flv, mpg, mts/m2ts, ts, mxf, webm, 3gp, ogv, vob, dv, y4m, gif and more.

Design notes

ffmpeg is called as a process, not linked as a library. That keeps Vidnux free of any codec licensing question of its own, lets it use whatever ffmpeg your distribution already trusts, and means the command it runs is one you can copy into a terminal and check yourself.

The interface follows your desktop. Light or dark is read from the XDG desktop portal, then gsettings, then GTK_THEME — and it follows a change live, without a restart. If none of them answer, it stays light.

No telemetry, no network calls, no account. The only thing Vidnux ever reaches for outside your machine is this page, and only when you press the ? button.
